공식 Claude Code 확장에 백도어, 확장 삭제로는 안 끝납니다

원문: Cursor Marketplace의 Claude Code for VS Code 확장 프로그램에서 백도어 발견 · phorion.io · 2026년 10월 30일 공개

한 줄 요약

Phorion은 Cursor Marketplace에 올라온 공식 Claude Code for VS Code 2.1.313 번들에서 SSH(Secure Shell, 원격 접속 프로토콜) 백도어를 발견했다고 밝혔습니다. 악성 코드는 확장의 정상 활성화 함수보다 먼저 실행됩니다. 공격자 공개키를 심고 외부 서버로 역방향 SSH 터널을 열며, 재부팅 뒤에도 터널을 다시 여는 장치를 설치합니다.

무엇을 했나 원문 내용

Phorion 글을 읽고 핵심을 정리해봤습니다. Cursor Marketplace는 Cursor 편집기용 확장을 배포하는 곳입니다. 확장은 IDE와 그 IDE를 실행한 사용자의 권한을 그대로 가집니다. 그래서 모듈이 로드되는 순간 로컬 파일, 소스 코드, 개발 도구에 접근할 수 있습니다. 원문에 따르면 해당 릴리스는 마켓플레이스에서 내려갔습니다. NPM(Node.js 패키지 저장소)과 VS Code 쪽 2.1.313 버전도 각 레지스트리에서 내려갔습니다. 분석은 macOS 중심이고, Linux·Windows는 차이점과 버그만 짚습니다.

악성 코드는 압축된 extension.js 맨 앞에 붙은 IIFE(즉시 실행 함수 표현식)입니다. 나머지 번들은 정상 확장과 같은 모습입니다. 이 코드는 Node가 파일을 읽자마자 실행되며, 확장의 activate(활성화) 함수보다 먼저 돕니다. 원문은 사용자가 확장을 건드리지 않아도 동작한다고 설명합니다. 이후 동작은 네 단계로 나뉩니다.

  • SSH 접근 준비: 사용자 홈 폴더의 .ssh 폴더 안 authorized_keys 파일에 공격자 공개키(주석 svc-telemetry)를 추가합니다. 이미 추가됐는지는 키가 아니라 주석 문자열로 확인합니다. 그래서 원문은 주석 대신 공개키 지문으로 찾으라고 권합니다. 이어서 OS별로 SSH 서버를 켜려 합니다. 다만 권한 상승 공격 코드는 없고, 비밀번호 없는 sudo가 설정돼 있지 않으면 sudo -n은 실패합니다.
  • 역방향 터널: 따로 내장한 개인키(주석 svc-telemetry-tun)를 임시 폴더에 .stk_ 파일로 씁니다. 그 키로 134.209.82[.]225에 SSH 연결을 엽니다. 공격자 서버가 연 포트로 들어온 연결은 터널을 거쳐 피해 PC의 SSH로 전달됩니다. 공격자는 첫 단계에서 심은 키로 로그인합니다. 연결은 IDE와 분리된 재시도 루프 안에서 60초 간격으로 다시 시도되므로, IDE를 닫아도 유지됩니다.
  • 재부팅 대비: macOS에서는 사용자 LaunchAgents 폴더에 com.apple.sysmond.plist라는 LaunchAgent(로그인 때 자동 실행되는 macOS 사용자 작업)를 만듭니다. Apple 구성 요소처럼 보이는 이름이며, 홈 폴더의 .config 폴더에 숨긴 .smt 스크립트를 실행합니다. Linux는 crontab(예약 실행 목록)의 @reboot 항목을 씁니다. Windows는 SysMon이라는 예약 작업이나 시작 프로그램 폴더를 씁니다.
  • 호스트 정찰: 설정 1.5초 뒤 수집한 정보를 HTTP로 한 번 보냅니다. 호스트 이름, 사용자 이름, Git 전역 이메일, 공인 인터넷 주소가 들어갑니다. 이름에 키·토큰·비밀·비밀번호·AWS·GCP를 뜻하는 단어가 들어간 환경 변수 이름도 최대 40개까지 포함됩니다. 값은 빼고 이름만 보냅니다. 원문은 이를 어느 PC에 어떤 자격 증명이 있는지 파악하는 용도로 봅니다.

원문이 따로 짚은 부분은 macOS 쪽 버그입니다. 스크립트는 관리자 권한 없이 systemsetup -getremotelogin을 실행합니다. 출력에 Off가 있을 때만 sudo -n으로 Remote Login(macOS 원격 로그인 설정)을 켭니다. 그런데 일반 사용자가 이 명령을 실행하면 Off 대신 관리자 권한이 필요하다는 오류 문장이 나옵니다. 그러면서도 종료 코드는 정상으로 끝납니다. 결국 켜는 단계를 통째로 건너뜁니다. SSH가 원래 꺼져 있던 Mac에서는 터널이 연결돼도, 되돌아온 연결이 닫힌 포트에서 막힙니다. 하지만 공개키와 재부팅 대비 장치는 그대로 설치됩니다.

탐지와 정리 방법도 나와 있습니다. 공개키 추가는 셸 명령이 아니라 Node의 fs.appendFileSync로 이뤄집니다. 그래서 echo·tee 같은 명령을 감시하는 규칙으로는 잡히지 않습니다. 원문은 두 가지를 보라고 권합니다. 하나는 Code Helper·Cursor Helper 같은 IDE 보조 프로세스가 authorized_keys 파일을 쓰는지입니다. 다른 하나는 Apple이 아닌 프로세스가 com.apple.* 이름의 LaunchAgent를 만드는지입니다. 터널로 들어온 로그인은 SSH 기록에 로컬 주소에서 온 것으로 남습니다.

확장 삭제만으로는 백도어가 사라지지 않습니다. 원문이 정리한 대응 순서는 다음과 같습니다. 터널 프로세스를 종료하고 지속 장치를 삭제합니다. 공격자 키와 임시 키 파일을 지우고 Remote Login 상태를 확인합니다. 마지막 항목은 SSH가 켜져 있었거나 로그인 흔적이 있을 때 그 계정이 접근할 수 있던 자격 증명을 교체하는 것입니다. 원문 끝의 침해 지표 표에는 악성 extension.js 해시, 두 키의 지문, 네트워크·파일 흔적이 모여 있습니다.

한계·반론 원문 내용

  • macOS 버그는 방어 수단이 아닙니다. Remote Login이 이미 켜져 있었거나 사용자가 나중에 켜면 백도어가 바로 동작한다고 원문은 경고합니다. 공개키 추가, 재부팅 대비 장치, 정찰 정보 전송은 이 버그와 관계없이 실행됩니다.
  • 분석 범위가 macOS에 치우쳐 있습니다. Linux·Windows는 차이점과 버그만 짚습니다. Linux crontab 확인 로직이 반복 실행 때 기존 예약 작업을 지울 수 있다고 적었지만, 예고한 상세 설명은 전문에 없습니다.
  • 침투 경로가 빠져 있습니다. 악성 코드가 어떻게 공식 번들에 들어갔는지는 다루지 않습니다. 실제로 공격자가 터널로 로그인한 사례가 있는지도 다루지 않습니다. 비컨을 로컬 주소로도 보내는 이유는 샘플만으로는 알 수 없다고 밝힙니다.
  • 보안 업체의 제품 소개를 겸한 글입니다. 자사 탐지 규칙이 이 공격의 지속 장치를 잡는다고 하지만, 탐지율 같은 독립 검증 결과는 함께 제시하지 않습니다.

🛠️ 기술

결론부터 말하면, AI 코딩 도구 확장은 설치 프로그램과 같은 수준으로 관리해야 한다고 봅니다. 저는 이 샘플을 직접 실행해 보지 않았습니다. 아래 판단은 원문이 공개한 코드와 표를 근거로 합니다. 원문 자체는 잘 쓴 대응 문서입니다. 코드 조각, 흔적 경로, 정리 순서가 한 글에 다 있습니다. 이번 확장은 사용자가 아무것도 누르지 않아도 로드 순간 실행됐습니다. '공식 마켓플레이스에 공식 이름이니 안전하다'는 가정, 이게 맞을까요? IDE 바이너리 서명이 정상이어도 확장 호스트 프로세스는 SSH 키 파일을 고칠 수 있었습니다. 공격자가 왜 AI 코딩 도구를 골랐는지는 원문에 없습니다. 다만 원래 파일을 읽고 셸을 실행하는 도구라 이상 행동이 덜 눈에 띈다는 점도 작용했을 것으로 봅니다. 팀에서는 확장 버전을 고정하고, 새 버전은 며칠 지켜본 뒤 들이는 방식부터 시작하면 좋겠습니다. 탐지 기준도 바꾸면 좋겠습니다. 명령 이름을 보는 대신 'IDE 보조 프로세스가 SSH 키 폴더나 LaunchAgents 폴더에 파일을 쓰는가'를 보는 편이, 이번처럼 셸을 거치지 않는 공격을 더 잘 잡습니다.

다른 곳에도 쓸 교훈은 오히려 공격자의 버그에 있습니다. '확인할 권한 없음'이 '꺼져 있지 않음'으로 처리됐습니다. 정상 종료 코드만 믿고 출력 형태를 검증하지 않은 탓입니다. 공격자 코드도 QA가 부족했던 셈이죠. 에이전트 하네스나 배포 스크립트의 상태 확인 함수도 같은 실수를 하기 쉽습니다. 상태는 켜짐·꺼짐·모름 세 가지로 돌려주고, '모름'이면 조용히 넘어가지 말고 기록을 남기게 만들어야 합니다. 방어 규칙도 똑같습니다. systemsetup -setremotelogin on 실행을 탐지의 필수 조건으로 걸었다면 이번 건은 놓쳤을 겁니다. 한 신호가 빠져도 다른 신호로 잡히도록 규칙을 여러 겹으로 두는 구조가 결국 품질을 만듭니다.

💼 사업

사업 쪽 결론은 개발자 편집기의 추가 기능도 회사가 구매하는 소프트웨어처럼 관리해야 한다는 것입니다. 확장 프로그램은 코드 편집기에 덧붙이는 추가 기능입니다. 이번에는 공식 이름을 단 추가 기능 하나가 외부에서 개발자 PC로 들어올 수 있는 통로를 만들었습니다. 개발자 PC에는 소스 코드와 클라우드 서비스 접속 열쇠(API 키)가 모여 있습니다. 그래서 한 대가 뚫리면 회사 전체 계정의 열쇠를 바꾸는 작업으로 이어질 수 있습니다. 확장을 지우는 것으로 끝나지 않으니, 보안 담당 인력과 시간이 따로 드는 셈이죠.

당장 할 일은 세 가지면 됩니다. 첫째, 팀 PC에 깔린 확장과 버전 목록을 만듭니다. 둘째, 문제 버전이 보이면 보안 담당이나 외부 사고 대응 업체에 바로 넘깁니다. 셋째, 앞으로는 새 버전을 자동으로 바로 받지 않고 잠시 지켜본 뒤 들이는 규칙을 둡니다. AI 코딩 도구 도입을 늘리는 중이라면 이 관리 규칙을 도입 계획에 같이 넣는 게 맞습니다. 팀 PC에 깔린 확장 목록을 지금 바로 뽑아 볼 수 있으신가요?
