CoworkOS: 벤치마크는 박빙, 자동 사후 학습은 +9.76

원문: CoworkOS:Scaling Agent Coworkers for Real-world Automation · arXiv(논문 공개 사이트) 2611.03178 · 2026년 11월 2일 공개

한 줄 요약

CoworkOS는 '무엇을 할지, 누구에게 맡길지, 결과를 받아들일지'는 모델이 정하고, 상태와 피드백 관리는 런타임이 맡도록 역할을 나눈 하네스입니다. 같은 모델로 돌린 12개 벤치마크에서 기존 공개 하네스인 OpenHands·Codex·DSH(DeepSeek Harness)와 비교해 네 영역 평균 모두 상위 두 자리 안에 들었습니다. 또 다섯 라운드 자동 사후 학습으로 학습 대상 모델의 여덟 개 벤치마크 평균을 33.19에서 42.95로 올렸습니다.

무엇을 했나 원문 내용

원문은 일을 맡기는 에이전트에게 두 가지가 함께 필요하다고 봅니다. 하나는 코드·문서·디자인 같은 결과물을 끝까지 만들어 내는 복잡한 작업입니다. 다른 하나는 며칠씩 이어지는 학습 실행이나 외부 변화를 지켜보다가 필요할 때만 움직이는 장기 모니터링입니다. 이를 위해 하네스(모델을 감싸 도구 호출·상태·피드백을 관리하는 실행 틀)를 세 층으로 나눴습니다. Main Agent(총괄 에이전트)는 계획을 세우고 일을 맡기며, 돌아온 결과를 받아들일지 판단합니다. Coordinator Runtime(조정 런타임)은 맡긴 일의 배정·진행 상태·대기 중인 피드백을 모델 바깥의 영구 상태로 저장하고 전달합니다. Subagent(하위 에이전트)는 분리된 컨텍스트에서 맡은 범위만 처리합니다. 원문은 위임을 evidence contract(증거 계약)라고 부릅니다. 목표·제약·권한과 함께 돌려받을 증거의 형태까지 정해서 넘기고, 하위 에이전트는 한 일과 아직 불확실한 점을 함께 보고합니다. 비동기로 맡긴 일의 결과는 Inbox(수신함)에 쌓였다가 다음 판단 시점에 총괄 에이전트에게 들어갑니다.

사람과의 협업은 공유 애플리케이션 층이 맡습니다. 문서, 프레젠테이션, CAD(컴퓨터 지원 설계) 모델, Blender(입체 모델 제작 도구) 장면은 플랫폼이 직접 관리하고, 기존 소프트웨어는 MCP로 연결합니다. 모든 수정은 '기준 버전이 현재 버전과 같을 때만 반영하고, 다르면 충돌로 돌려보낸다'는 규칙을 따릅니다. 이 규칙은 사람과 에이전트에게 똑같이 적용됩니다. 작업 연속성도 런타임이 관리합니다. 오래 걸리는 계산은 Job(백그라운드 작업)으로 돌려 로그를 남깁니다. 외부 상태 감시는 스크립트가 저장된 기준과 비교해, 바뀐 게 없으면 모델을 부르지 않습니다. 기다리기로 할 때 감시 대상이나 다음 점검 시각이 없으면 런타임이 대기를 거부합니다. 실험 장부는 실행 파일에서 읽은 측정값과 보고서 문장에만 있는 값을 구분해 기록합니다.

평가는 두 갈래입니다. 첫째, 네 하네스를 모두 GLM(실험 전체에 쓴 중심 언어 모델 계열)의 GLM-5.3 모델과 컨텍스트 256K 토큰 설정으로 맞춰 12개 벤치마크를 돌렸습니다. 원문 표의 영역별 평균을 정리하면 다음과 같습니다. 생산성 업무(Productivity)는 CoworkOS가 57.54로 DSH의 56.13보다 높았습니다. 도구 사용(Tool Use)은 CoworkOS가 55.22로 DSH의 55.31보다 낮았습니다. 검색(Search)은 CoworkOS가 82.14로 OpenHands의 82.22보다 낮았습니다. ML 코딩 영역 평균은 CoworkOS가 가장 높았습니다. 이와 별도로 웹사이트·게임·프레젠테이션·CAD·Blender 결과물 24개 사례를 Codex·DSH 결과물과 나란히 놓고 비교했습니다.

둘째는 에이전트가 사후 학습(이미 만든 모델을 추가 데이터로 더 가르치는 과정)을 직접 돌리는 RSI(재귀적 자기개선, AI가 자기 개선 과정에 직접 참여하는 방식) 실험입니다. GLM-5.3이 실험 지휘와 학습 데이터 생성을 맡았고, Qwen3.6-35B-A3B가 학습 대상 모델입니다. 한 라운드는 '평가 → 약점 진단과 데이터 파이프라인 수정 → 데이터 생성·검증·필터링 → SFT(지도 미세조정) → 재평가' 순서로 돕니다. 다섯 라운드 뒤 여덟 개 벤치마크 평균이 33.19에서 42.95로 9.76점 올랐습니다. 가장 크게 오른 항목은 AutomationBench(업무 자동화 벤치마크)의 +33.15였습니다. 세 번째 라운드에는 학습 궤적의 78.3%가 이 영역 데이터였습니다. 점수가 한 방향으로만 오르지는 않았습니다. 두 번째 라운드에서는 처음 쓰는 135개 궤적을 24번씩 반복 학습했고, 평균은 36.94에서 35.90으로 떨어졌습니다. 점검 결과 42개 궤적이 지도 토큰의 84.2%를 차지하고 있었습니다. 세 번째 라운드에서는 데이터를 558개 궤적으로 넓혔고, 평균은 39.22로 회복했습니다. 마지막 라운드에서는 새 궤적의 61.1%를 함수 호출 데이터로 채웠고, BFCL(함수 호출 벤치마크) v4가 직전 라운드보다 9.07점 올랐습니다. 최종적으로 초기보다 낮게 끝난 벤치마크는 JobBench(직무 과제 벤치마크) 하나입니다.

한계·반론 원문 내용

  • 벤치마크 차이가 작습니다. 원문은 네 하네스 중 종합 성능이 가장 강하다고 쓰지만, 영역 평균으로 보면 도구 사용·검색에서는 다른 하네스가 앞서고 생산성 업무 차이도 크지 않습니다. 표에는 반복 실행 횟수나 점수 편차가 없습니다. 원문도 점수는 이번 실행에 쓴 실제 설정을 설명할 뿐이라고 밝혔습니다.
  • 모든 하네스가 GLM-5.3 한 모델 위에서 돌았습니다. 초록의 'Codex·DeepSeek Harness 같은 프런티어 에이전트 앱과 견줄 만하다'는 문장은 하네스만 바꾼 비교로 읽어야 합니다. 다른 모델에서도 같은 순위가 나오는지는 원문이 확인하지 않았습니다.
  • 자동 사후 학습의 라운드별 변화는 여러 개입이 동시에 들어간 결과라 개별 원인을 가를 수 없습니다. 라운드 번호가 경과 시간을 뜻하지 않는다는 점도 원문이 직접 밝혔습니다. 사람이 짠 학습 루프나 다른 하네스와의 비교군이 없고, 학습에 든 비용과 시간도 나오지 않습니다.
  • 24개 정성 비교 사례는 결과물을 눈으로 본 관찰이며, 원문도 우위가 사례마다 갈린다고 인정합니다. VESPER(원문의 스피커 구조 시각화 사례 이름) Speaker에서는 CoworkOS 결과물의 내부 분리가 잘 드러나지 않았습니다. Saturn Atlas(행성 단면 시각화 사례)에서는 Codex의 단면이 내부 층을 더 선명하게 구분했습니다. CAD는 매개변수 편집 가능성·간섭 없는 조립·공차·제조 가능성·작동 성능을, Blender는 소품 지지와 충돌을 검증하지 않았다고 원문이 명시했습니다.

🛠️ 기술

결론부터 말하면, 이 논문에서 가져갈 것은 벤치마크 순위가 아니라 운영 규칙입니다. 같은 모델로 돌리면 상위 하네스 간 차이는 영역마다 선두가 바뀌는 수준입니다. 그래서 이 표만 보고 하네스를 바꿀 이유는 약합니다. 반면 다음 세 규칙은 어떤 멀티 에이전트 시스템에도 그대로 옮길 수 있습니다. '기다릴 때는 감시 대상이나 점검 시각이 꼭 있어야 한다', '기준 버전이 다르면 사람 수정이든 에이전트 수정이든 충돌로 돌려보낸다', '하위 에이전트는 불확실한 점까지 보고한다'입니다. 실험 장부가 파일에서 읽은 수치와 보고서 문장 속 수치를 따로 기록하는 설계는 확실히 잘했습니다. 에이전트가 '좋아졌다'고 적은 숫자를 확인 없이 다음 판단에 쓰면, 루프는 실제 성능이 아니라 자기 보고를 따라가는 셈이죠.

자동 사후 학습에서 얻은 교훈도 다른 데이터 루프에 그대로 쓸 수 있습니다. 두 번째 라운드의 하락은 샘플 개수만 보고 데이터를 고르면 소수의 긴 궤적이 학습 신호 대부분을 차지할 수 있다는 점을 보여 줍니다. 에이전트에게 데이터 루프를 맡긴다면 샘플 수와 함께 샘플별 토큰 점유율을 매 라운드 기록하게 해봅시다. 다만 AutomationBench의 +33.15는 데이터가 몰린 영역에서 나온 결과입니다. 그래서 '에이전트가 전략을 잘 짰다'와 '한 영역에 데이터를 많이 넣었다'를 지금 자료로는 구분하기 어렵습니다. 이게 맞을까요? 저는 사람이 짠 데이터 레시피와 같은 예산으로 나란히 돌린 비교가 나오기 전까지는 'RSI 동료'라는 표현을 아껴 두는 편이 맞다고 봅니다.

💼 사업

사업 쪽에서 볼 숫자는 +9.76보다 '같은 모델을 쓰면 상위 하네스들의 점수 차이가 작다'는 사실입니다. 에이전트 제품을 고를 때 점수표만으로는 차이를 가리기 어렵습니다. 실제 차이는 세 군데에서 나옵니다. 작업이 끊겼다가 정확히 이어지는지, 사람이 고친 내용을 에이전트가 덮어쓰지 않는지, 누가 언제 무엇을 바꿨는지 기록이 남는지입니다. 도입 검토표에 이 세 가지를 따로 넣는 것부터 해봅시다.

자동 사후 학습은 연구원이 반복하던 '평가하고, 데이터를 고치고, 다시 학습하는' 일을 에이전트에게 맡기는 방향을 보여 줍니다. 다만 원문에 학습 비용과 소요 시간이 없어서 ROI(투자 대비 효과)는 아직 계산할 수 없습니다. 에이전트가 밤새 학습을 돌려 줬다면 다음 날 아침에 받아야 할 건 점수표보다 영수증입니다. 팀에서는 에이전트가 보고한 수치가 어디서 나왔는지 따로 확인하고 계신가요?
